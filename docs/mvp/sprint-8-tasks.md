# Sprint 8 — V1.1: Natural language quick add

Источник: [nextjs-personal-scheduling-assistant-mvp-plan.md](./nextjs-personal-scheduling-assistant-mvp-plan.md), §18 «Что добавить сразу после MVP», раздел **V1.1 — Natural language**: поле «Что нужно сделать?», пользователь пишет свободным текстом («Завтра в 19 тренировка на час»), LLM преобразует это в `TaskDraft`. План не определяет спринтов после Sprint 7 (§19 заканчивается на нём — Sprint 7 был явно последним перед первыми пользователями), поэтому этот документ — первый спринт, которого нет в исходном плане; структура и разбивка на задачи ниже написаны сейчас, по тому же принципу, что и предыдущие спринты. Продолжение [sprint-7-tasks.md](./sprint-7-tasks.md) — Sprint 7 смержен (PR [#7](https://github.com/Natalka-qa/Reminder-assistant/pull/7), в `main`), ветка `sprint-8-tasks` ответвляется от `main`.

**Цель спринта:** добавить необязательный способ создать задачу свободным текстом вместо (не вместо навсегда, а как альтернативу) ручного заполнения формы — поле «Что нужно сделать?» на `/tasks/new`, кнопка «Заполнить из текста», LLM возвращает черновик, пользователь видит его в уже существующей форме, проверяет/правит и сохраняет как обычно. Никакой новой бизнес-логики создания задачи не добавляется — LLM только заполняет то же самое `CreateTaskInput`, дальше работает существующий `taskService.createTask` (валидация, конфликты, recurrence, уведомления) без изменений.

**Sprint Definition of Done**

- [ ] `npm run build`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run format:check` зелёные; CI на PR проходит.
- [ ] На `/tasks/new` есть поле свободного текста и кнопка, заполняющая остальные поля формы (Title/Date/Time/Duration, best-effort Priority/Repeat) из текста вроде «Завтра в 19 тренировка на час».
- [ ] Результат парсинга не создаёт задачу напрямую — только предзаполняет уже существующую форму; создание идёт через тот же `createTaskAction`, что и раньше (конфликты, валидация — без дублирования).
- [ ] Ошибка/недоступность LLM (сеть, таймаут, невалидный ответ) не ломает страницу — форма остаётся пустой/как была, показывается сообщение, пользователь может заполнить вручную.
- [ ] `ANTHROPIC_API_KEY` — новая переменная окружения, задокументирована в `.env.example` и объявлена в `src/lib/env.ts`; **необязательная** (см. «Расхождения» п.8) — без неё остальное приложение и CI работают как обычно, а поле/кнопка на `/tasks/new` просто не рендерятся.
- [ ] Слоистая архитектура не нарушена: вызов Anthropic SDK — только в новом `*.service.ts`, не в компоненте/action напрямую (тот же принцип, что и для Prisma в ADR-001).
- [ ] Новые тесты на чистую логику маппинга (draft → `TaskFormValues`, резолвинг даты "today"/"tomorrow" в timezone пользователя) зелёные — сам вызов LLM не мокается тестами (см. «Не входит»).

## 1. Стартовое состояние (аудит по факту)

| Область | Что нашли |
|---|---|
| **Создание задачи сейчас** | Только вручную: `/tasks/new` → `TaskForm` (`task-form.tsx`) с явными полями Date/Time/Duration/Priority/Flexibility/Repeat/Reminder → `createTaskAction` (`features/tasks/actions.ts`) → `taskService.createTask` (`features/tasks/task.service.ts`), который валидирует через `createTaskSchema` (`lib/validation/task.ts`), проверяет конфликты (`conflictService`), создаёт occurrence(-ы) и уведомления в одной транзакции. |
| **Форма** | `TaskForm` уже держит каждое поле в контролируемом React state (`title`, `description`, `date`, `time`, `durationMinutes`, `priority`, `flexibility`, `repeatFrequency`, `repeatDaysOfWeek`, `reminderOffsetMinutes`) — то есть предзаполнить её после монтирования (без перезагрузки страницы) можно набором `setState`, ничего в архитектуре формы менять не нужно. `/tasks/new` задаёт дефолты: `date=сегодня`, `time=09:00`, `durationMinutes=30`, `priority=NORMAL`, `flexibility=FLEXIBLE`, `repeatFrequency=NONE`, `reminderOffsetMinutes=5` — те же дефолты имеет смысл использовать для полей, которые LLM не смогла извлечь из текста. |
| **Схема данных** | `createTaskSchema` — источник истины для формы задачи: `date`/`time` — строки `YYYY-MM-DD`/`HH:mm` (те же форматы, что отдают `<input type="date">`/`<input type="time">`), `durationMinutes` 0–1440, `priority`/`flexibility` — enum, `repeatFrequency`/`repeatDaysOfWeek` — recurrence (WEEKLY требует хотя бы один день). Любой draft от LLM должен в итоге лечь в эту же форму значений — по сути, LLM решает одну конкретную задачу: свободный текст → значения этих же полей. |
| **Таймзона / "сегодня"** | `zonedNow(timezone)` (`lib/date`) уже даёт "сейчас" в таймзоне пользователя — то же, чем пользуется `/calendar`. Без этого «завтра» в тексте резолвится неправильно (сервер работает в UTC). |
| **LLM / внешние API** | Не используется нигде в проекте. Нет `@anthropic-ai/sdk` (или любого другого AI SDK) в `package.json`, нет соответствующей переменной окружения в `.env.example`/`src/lib/env.ts`. Это первая интеграция с внешним LLM в проекте. |
| **Паттерн внешних секретов** | Есть отработанный паттерн для новых секретов (`GOOGLE_CLIENT_ID`, `RESEND_API_KEY`, `CRON_SECRET`, ...): добавить в `.env.example` с комментарием, добавить в `serverEnvSchema` (`lib/env.ts`), использовать через `env.X`, никогда не читать `process.env` напрямую вне `env.ts`. |
| **Обработка ошибок сервисного слоя** | Sprint 7 (S7-05) завёл паттерн: внешний вызов может упасть, клиентский компонент ловит это и показывает `toast.error(...)`, не даёт необработанному исключению дойти до пользователя молча. Тот же паттерн подходит для сбоя LLM-вызова. |

### Расхождения плана / решения на этот спринт

1. **Провайдер — Anthropic Claude API через `@anthropic-ai/sdk`, structured tool-calling, не свободный текст + ручной JSON.parse.** План (§18) говорит просто «LLM», не называет провайдера. Проект уже живёт в экосистеме Claude Code/Anthropic — это самый естественный выбор без дополнительного онбординга нового провайдера. Tool-calling (одна tool-схема с полями, зеркалящими `createTaskSchema`) вместо парсинга произвольного текстового ответа — устраняет целый класс багов «модель вернула не совсем JSON». Конкретный `model` id и параметры вызова — уточняются в момент реализации через актуальную информацию по Claude API (id меняются быстрее, чем живут такие документы), не фиксируются здесь.
2. **LLM не создаёт задачу напрямую — только предзаполняет существующую форму, создание — тем же путём, что и раньше.** Раз `taskService.createTask` уже инкапсулирует всю бизнес-логику (конфликты, recurrence, транзакция), дублировать её ради AI-flow — не нужно и рискованно (два места, которые могут разойтись). LLM отвечает только за один шаг: текст → значения полей формы. Ошибка модели (неверная дата, не та длительность) — не теряет данные пользователя и не создаёт задачу молча, а видна и правится в уже привычном UI.
3. **Точка входа — необязательное поле на `/tasks/new`, не отдельная страница/чат.** Проще всего интегрировать в существующий флоу, не плодить второй способ навигации. Кнопка «Fill from text» вызывает новый server action, результат — `setState` по уже существующим полям `TaskForm` (форма это уже умеет, см. аудит). Ничего не меняется для пользователей, которые продолжают заполнять форму руками — поле полностью необязательное.
4. **Без уточняющих вопросов от LLM при неоднозначном вводе — просто явный отказ с сообщением, дальше форма как обычно.** Диалоговый уточняющий флоу («когда именно завтра?») — это по сути V1.2/чат-интерфейс, не «одно поле → один парсинг» из V1.1. Если модель не уверена в дате/времени/названии — возвращает `{ ok: false, message }`, кнопка показывает это как обычную ошибку (toast), пользователь просто дозаполняет форму вручную — ни один сценарий не становится тупиковым.
5. **Recurrence/priority — best-effort в той же tool-схеме, не отдельная задача.** Раз tool-схема и так описывает все поля `CreateTaskInput`, добавить туда `repeatFrequency`/`priority` как необязательные поля почти не увеличивает сложность промпта — включаем сразу, но не пишем под это отдельных исчерпывающих тестов (см. «Не входит») — это «bonus», не то, что явно требует план.
6. **Без хранения драфтов.** Ни таблицы в БД, ни сессии переписки — один синхронный вызов (server action), ответ либо ложится в форму, либо нет. Тот же принцип, что уже применялся против Sentry/Inngest/интеграционных тестов в предыдущих спринтах — не вводить инфраструктуру, для которой пока нет реальной необходимости.
7. **Тесты — только чистая логика вокруг LLM-вызова, не сам вызов.** Реальный API-запрос к Anthropic не мокается и не тестируется в `npm run test` (нужен бы был либо реальный ключ в CI, либо сложный мок — оба варианта не стоят того на этом масштабе). Тестируем то, что не требует сети: маппинг результата tool-вызова в `TaskFormValues` (типы/дефолты для отсутствующих полей) и резолвинг относительных дат ("today"/"tomorrow"-подобных плейсхолдеров) в таймзоне пользователя, если эта логика не полностью делегирована промпту.
8. **`ANTHROPIC_API_KEY` — необязательная переменная, не обязательная, как изначально планировалось в Sprint DoD.** У разработчика нет доступа к ключу (Anthropic API требует привязку способа оплаты в консоли, заводить её сейчас нет возможности). Раз вся фича и так уже спроектирована как необязательная надстройка над формой (п.2–3), естественно распространить это и на конфигурацию: `env.ts` не падает при отсутствии ключа, `task-draft.service.ts` (`isTaskDraftEnabled()`) сообщает об этом странице, и `/tasks/new` просто не рендерит поле/кнопку — вместо того, чтобы (как для остальных секретов) не давать всему приложению запуститься. Ключ можно добавить в любой момент позже, ничего в коде менять для этого не нужно.

## 3. Задачи

### S8-01 · Инфраструктура

**Что сделать**
- `npm install @anthropic-ai/sdk`.
- `.env.example` — добавить `ANTHROPIC_API_KEY` с комментарием (где взять, зачем нужен, что он необязательный).
- `src/lib/env.ts` — добавить `ANTHROPIC_API_KEY: z.string().optional()` в `serverEnvSchema` (см. «Расхождения» п.8 — сознательно не по образцу `RESEND_API_KEY`, тот обязательный).

**Acceptance criteria**
- [ ] Запуск без `ANTHROPIC_API_KEY` в `.env.local` проходит нормально — `env.ts` не бросает исключение, только фича «Fill from text» выключена (`isTaskDraftEnabled()` в `task-draft.service.ts` возвращает `false`).

### S8-02 · `task-draft.service.ts`

**Что сделать**
- `src/features/tasks/task-draft.service.ts` — единственное место, где импортируется `@anthropic-ai/sdk` (по аналогии с ADR-001: Prisma — только в `*.repository.ts`, здесь тот же принцип для внешнего AI-клиента).
- Tool-схема с полями `CreateTaskInput` (без `confirmConflicts` — это UI-стейт, не то, что можно извлечь из текста): `title` (обязательно), `description?`, `date`, `time`, `durationMinutes?`, `priority?`, `flexibility?`, `repeatFrequency?`, `repeatDaysOfWeek?`.
- Промпт получает: сырой текст пользователя + текущую дату/день недели в таймзоне пользователя (`zonedNow`), чтобы «завтра»/«в понедельник» резолвились верно.
- При отсутствии `title` или невозможности определить `date`/`time` — модель не должна выдумывать значения; в этом случае функция возвращает explicit failure (`{ ok: false, message }`), а не частично заполненный/угаданный черновик.
- Таймаут на вызов SDK (не давать запросу висеть бесконечно) и `try/catch` — сетевая ошибка/невалидный ответ тоже уходит в `{ ok: false, message }`, не бросает исключение наружу.

**Acceptance criteria**
- [ ] `parseTaskDraft("Завтра в 19 тренировка на час", { timezone, now })` при живом API-ключе возвращает `{ ok: true, draft: {...} }` с `date` = завтрашней датой в таймзоне пользователя, `time = "19:00"`, `durationMinutes = 60`, `title` похожим на «тренировка».
- [ ] Текст без определяемой даты/времени/названия → `{ ok: false, message }`, не исключение.

### S8-03 · Server action

**Что сделать**
- `src/features/tasks/actions.ts` (или отдельный файл рядом) — `parseTaskDraftAction(text: string)`: проверяет сессию (`getCurrentUser`), берёт таймзону пользователя, вызывает `taskDraftService.parseTaskDraft`, возвращает результат клиенту в уже существующем стиле `{ status: "success" | "error", ... }` (тот же паттерн, что `TaskActionState`/`OccurrenceActionState`).

**Acceptance criteria**
- [ ] Неаутентифицированный вызов возвращает `{ status: "error", message: "Not signed in." }`, как остальные actions.
- [ ] Успешный парсинг возвращает данные, готовые лечь прямо в `TaskFormValues` (типы уже совпадают с `createTaskSchema`).

### S8-04 · UI

**Что сделать**
- `TaskForm` (или `/tasks/new/page.tsx`, если проще держать вне переиспользуемого компонента, раз это сейчас нужно только при создании) — текстовое поле «What do you need to do?» + кнопка «Fill from text» (disabled во время запроса, как остальные async-кнопки в проекте).
- Поле/кнопка рендерятся только когда `isTaskDraftEnabled()` (`task-draft.service.ts`) вернул `true` — новый prop `showTextDraft` на `TaskForm`, включается только на `/tasks/new` (см. «Расхождения» п.8: без ключа фичи попросту не видно, не placeholder с ошибкой).
- Успешный результат — `setState` по существующим полям формы (`setTitle`, `setDate`, `setTime`, и т.д.), поля, которые LLM не извлекла, остаются на дефолтах `/tasks/new`.
- Ошибка — `toast.error(message)`, тем же паттерном, что уже есть в форме (см. `useEffect` на `state.status === "error"`).

**Acceptance criteria**
- [ ] Текст «Завтра в 19 тренировка на час» → после клика форма показывает завтрашнюю дату, 19:00, заголовок с «тренировка», Duration 60.
- [ ] Дальнейшее создание задачи из предзаполненной формы идёт тем же путём (submit → `createTaskAction`), включая диалог конфликтов, если он возникает.
- [ ] Без `ANTHROPIC_API_KEY` в окружении поле/кнопка не отображаются на `/tasks/new`; форма создания задачи иначе не отличается от обычной.

## 4. Не входит в Sprint 8

Сознательно откладываем: голосовой ввод (V1.2), Telegram-бот (V1.3), чтение Google Calendar (V1.4), умный поиск свободных окон (V1.5), поведенческая аналитика (V1.6) — каждый из них отдельный по объёму пункт плана, не расширение одного текстового поля; уточняющий диалоговый флоу при неоднозначном тексте — сейчас просто явный отказ с сообщением; хранение истории/черновиков распознавания; тесты, реально бьющие в Anthropic API (см. «Расхождения» п.7); замена ручной формы AI-полем — это строго дополнительный, необязательный путь.

## 5. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| Стоимость/задержка внешнего API-вызова на каждый клик | Лишние расходы, пользователь ждёт | Быстрая/дешёвая модель для структурного извлечения (не «think hard» модель), короткий таймаут, вызов только по явному клику — не автоматически при вводе текста |
| Модель возвращает данные вне допустимых значений схемы (например `durationMinutes` отрицательное или не число) | Форма могла бы принять мусорные значения | Draft всё равно проходит через ту же `createTaskSchema` при финальном submit (S8-02 не подменяет валидацию, только предзаполняет) — а на этапе S8-02 сама tool-схема уже ограничивает форму ответа модели |
| `ANTHROPIC_API_KEY` не настроен в проде при первом деплое после этого спринта | Приложение не стартует (как и с любым другим отсутствующим обязательным секретом) | Тот же паттерн, что уже работает для остальных секретов — явное сообщение при старте, README/`.env.example` обновлены заранее (S8-06) |
