# Sprint 7 — Polish: мобильная вёрстка, ошибки, тесты, деплой

Источник: [nextjs-personal-scheduling-assistant-mvp-plan.md](./nextjs-personal-scheduling-assistant-mvp-plan.md), раздел §19 «Sprint 7 — Polish» (mobile layout / timezone edge cases / error handling / loading states / empty states / tests / deployment), §20 «Definition of Done для MVP» — среди прочего явно требует «использовать приложение нормально с телефона». Последний спринт перед тем, как MVP можно отдавать первым пользователям (§19: «После этого MVP можно отдавать первым пользователям»). Продолжение [sprint-6-tasks.md](./sprint-6-tasks.md) — **Sprint 6 уже смержен** (PR [#6](https://github.com/Natalka-qa/Reminder-assistant/pull/6), в `main`), поэтому эта ветка (`sprint-7-tasks`) ответвлена от `main`, не от предыдущей sprint-ветки.

**Цель спринта:** закрыть накопившиеся за Sprint 1–6 огрехи, которые не были в фокусе фичевых спринтов — сломанную мобильную вёрстку, недостающие error/not-found/loading страницы, тихо проглатываемые ошибки, дыры в тестах граничных случаев таймзоны и полностью нерабочий `/calendar` (ссылка в навигации есть с Sprint 1, страницы никогда не было — 404 у любого, кто на неё нажмёт). В отличие от Sprint 2–6, здесь нет одной новой фичи — это чек-лист независимых, в основном небольших правок по факту аудита (см. §1).

**Sprint Definition of Done**

- [ ] `npm run build`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run format:check` зелёные; CI на PR проходит (все пять отдельно, см. урок Sprint 4).
- [ ] Форма создания/редактирования задачи не ломает вёрстку на 375px (iPhone SE) — ни один блок не обрезается по горизонтали, кнопки действий на dashboard переносятся, а не вылезают за карточку.

- [ ] Есть `error.tsx` и `not-found.tsx` уровня `src/app` — ошибка/404 на `/`, `/login` больше не показывают дефолтный экран Next.js.

- [ ] Новые тесты на DST fall-back (`addDaysInZone`, `zonedDateTimeToUtc`) и на ранее непокрытые `addMinutes`/`formatDateInZone`/`formatTimeInZone` зелёные.

### Расхождения плана / решения на этот спринт

1. **Мобильная вёрстка — точечные фиксы найденных мест, не редизайн.** Правим два конкретных `grid-cols-2` (на `grid-cols-1 sm:grid-cols-2`, тот же паттерн, что уже используется в shadcn-примитивах вроде `alert-dialog.tsx`), перенос кнопок occurrence-actions на новую строку при нехватке места, `truncate` на заголовках задач. Полного аудита каждого пикселя на каждом брейкпоинте не делаем — «использовать с телефона нормально» (§20 плана) про базовую функциональность, не про пиксель-перфект.
2. **Таймзона — закрываем дыры в тестах и один реальный UX-баг (баннер не персистит dismiss), не трогаем модель подтверждения.** Неподтверждённая таймзона по плану не должна ничего блокировать — это осознанно оставляем как есть. `localStorage` для dismiss выбран вместо записи в БД: это чисто клиентское «не показывай мне это снова в этой сессии браузера», не бизнес-данные пользователя, лишняя запись в БД ради этого — оверинжиниринг (тот же принцип, что уже применяется к browser-only настройкам в проекте).
3. **Обработка ошибок — root `error.tsx`/`not-found.tsx`, try/catch в cron-роутах, маппинг Prisma P2025 → доменные NotFound-ошибки на update/delete, общий фолбэк-toast в клиентских экшенах.** Не делаем интеграцию с Sentry/логированием — для соло-MVP это преждевременная инфраструктура (тот же аргумент, что уже был против Inngest в Sprint 5 и против backoff-восстановления в Sprint 6): `console.error` в error boundary достаточно на этом масштабе, реальный мониторинг — после первых пользователей, когда будет что мониторить.
4. **Loading — скелетоны только для Dashboard и `/tasks` (самые «тяжёлые» и самые частые страницы), не для всех шести.** `tasks/new`/`tasks/[id]/edit` — простые формы, рендерятся быстро, общий скелетон уровня layout для них достаточен; тратить время на форму-скелетон ради двух редко посещаемых страниц не оправдано в рамках одного спринта.
5. **Тесты — не переписываем архитектуру тестирования, только закрываем дыры в уже тестируемом слое чистых функций.** Проект с первого спринта тестирует только pure-функции (recurrence, date, validation, email-строители) и ни разу — репозитории/сервисы, трогающие Prisma; вводить integration-тесты (нужна тестовая БД или объёмные моки Prisma Client) в последнем «полировочном» спринте перед пользователями — смена конвенции по ходу дела, а не полировка. Добавляем только: DST fall-back для `addDaysInZone`/`zonedDateTimeToUtc`, и тесты для `addMinutes`/`formatDateInZone`/`formatTimeInZone`, которые уже используются в проде, но случайно остались без тестов.
6. **Деплой — то, что можно закрыть в коде репозитория, закрываем; настройку самого проекта на Vercel (env vars, домен, git-интеграция) делает пользователь руками, это не то, что можно сделать из кодовой базы.** В коде: `build`-скрипт запускает `prisma migrate deploy` перед `next build` (Vercel по умолчанию выполняет `npm run build`, так миграции гарантированно применяются перед стартом новой версии), добавляем `/api/health` (простой пинг БД, без авторизации — нужен внешним аптайм-мониторам), дописываем в README секцию Deployment с шагами и списком env vars для Vercel. Сам деплой (нажать «Import Project» в Vercel, ввести секреты) — вне зоны кода, инструкция появится в README, но выполнить её должен пользователь.
7. **`/calendar` — реализуем минимальный список по плану (§16: «Today / Tomorrow / This week»), не полноценный календарный грид.** Это единственный пункт спринта, который добавляет новый UI, а не чинит существующий — но живая 404-ссылка в главной навигации явно противоречит «MVP готов для первых пользователей» сильнее, чем любой из остальных пунктов, и план прямо описывает эту страницу как часть MVP (§16), не post-MVP (§18 v1.1+ явно перечисляет то, что действительно отложено — Google Calendar integration и т.п., `/calendar` в этом списке нет). Переиспользуем уже существующие occurrence-запросы (`findForUserBetween`, `findUpcomingForUser`) вместо новой модели «календарного вида».

## 3. Задачи

### S7-01 · Адаптивная вёрстка

**Оценка:** 2 ч

**Что сделать**
- `task-form.tsx:213`, `task-form.tsx:253` — `grid grid-cols-2 gap-4` → `grid grid-cols-1 gap-4 sm:grid-cols-2` (Date+Time, Priority+Flexibility).
- `occurrence-actions.tsx` — контейнер кнопок Done/Partial/Skip/Snooze: `flex items-center gap-1` → `flex flex-wrap items-center justify-end gap-1`, чтобы на узком экране кнопки переносились на вторую строку, а не сжимались/обрезались.
- Заголовки задач в списках (`dashboard/page.tsx` `OccurrenceList`, `tasks/[id]/page.tsx`) — добавить `truncate` (с `min-w-0` на родительском flex-контейнере, иначе `truncate` не сработает во flex-разметке) на `<span>` с названием задачи.
- Заголовок `/tasks/[id]` (`flex items-start justify-between gap-4` с длинным названием + Edit/Deactivate/Delete) — на узком экране переносить кнопки под заголовок: `flex flex-col gap-4 sm:flex-row sm:items-start sm:justify-between`.

**Acceptance criteria**
- [ ] На эмуляции 375×812 (iPhone SE) ни один из перечисленных экранов не даёт горизонтальный скролл страницы.
- [ ] Длинное название задачи (60+ символов) обрезается с `…`, не разъезжается по строке.
- [ ] На 375px кнопки occurrence-actions видны все четыре (перенесены на новую строку при необходимости), ни одна не обрезана.

### S7-03 · Персистентность dismiss у onboarding-баннера

**Оценка:** 0.5 ч

**Что сделать**
- `onboarding-banner-client.tsx` — при клике на крестик, помимо `setDismissed(true)`, записать `localStorage.setItem("onboarding-banner-dismissed", "1")`; при монтировании читать это значение и не показывать баннер, если оно установлено. - [ ] Клик на крестик → баннер не появляется при следующей навигации в этой же вкладке/браузере.
- [ ] В приватном режиме (или с заблокированным `localStorage`) баннер по-прежнему рендерится и скрывается по клику в рамках текущей сессии (не крашится).

### S7-05 · Обработка ошибок: cron, гонки, клиентский фолбэк

**Оценка:** 2 ч

**Что сделать**
- `api/cron/extend-occurrences/route.ts`, `api/cron/send-notifications/route.ts` — обернуть вызов сервиса в `try/catch`; при ошибке вернуть `Response.json({ error: "..." }, { status: 500 })` вместо голого падения без тела (сообщение — общее, не текст исключения, наружу секреты/стектрейс не отдаём).
- `taskRepository.update`/`delete` (`task.repository.ts`) — поймать Prisma `P2025` (record not found — гонка между `findById`-проверкой в сервисе и самой мутацией) и перебросить как `TaskNotFoundError`, а не дать сырой `PrismaClientKnownRequestError` уйти из `runInTransaction` в action. То же самое для `occurrenceRepository.update` относительно `OccurrenceNotFoundError`, если применимо (симметрично).
- `occurrence-actions.tsx` (`run`/`runSnooze`) и `task-actions.tsx` (`handleDeactivate`/`handleDelete`) — обернуть `await action(...)` в `try/catch`; при перехвате неожиданного (не `status: "error"`, а брошенного) исключения показать `toast.error("Something went wrong. Please try again.")`, чтобы гонка/сетевой сбой не оставляли пользователя без всякой обратной связи.

**Acceptance criteria**
- [ ] Смоканная ошибка внутри `sendDueNotifications`/`extendOccurrencesForAllActiveTasks` даёт `500` с JSON-телом `{ error: ... }`, не пустой ответ.
- [ ] Удаление задачи в двух параллельных запросах (второй запрос после того, как первый уже удалил ту же задачу) — второй получает `TaskNotFoundError`-сообщение через `toast`, не необработанный reject в консоли.
